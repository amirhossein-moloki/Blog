# Enterprise Caching Architecture Documentation

This document describes the design, architecture, and usage of the **Enterprise Caching Subsystem** implemented in this project.

The architecture is built from the ground up to support high-traffic, low-latency, and highly scalable enterprise requirements.

---

## 1. Core Principles

- **Source of Truth:** PostgreSQL remains the single Source of Truth. Redis is utilized strictly as an optimization/speed layer.
- **Fail-Safe Fallback:** The application has a 100% transparent fallback to PostgreSQL and local-memory structures. No request fails because Redis is down or unavailable.
- **Strict Abstraction:** No view, controller, model, or middleware interacts with the cache engine directly. Every caching action in the codebase goes through the centralized `CacheManager` service.
- **Wildcard-Free Invalidation:** To prevent blocking Redis nodes, wildcard deletions (`keys *`) are prohibited. Invalidation is completely version-based, tag-based, and dependency-graph-driven.

---

## 2. Directory Structure

All cache-related components are housed in a modular, framework-independent structure within `common/cache/`:

```text
common/cache/
├── __init__.py          # Exports central service instances and wires components.
├── manager.py           # Implements the Central CacheManager with Cache-Aside & SWR.
├── policies.py          # Defines TTL levels, jitter generator, and canonical key builders.
├── serializers.py       # Pluggable serialization layer (JSON, MessagePack).
├── compressors.py       # Pluggable compression layer (Gzip, Zstandard) with size limits.
├── locks.py             # Thread-safe Distributed Locks with LocalMemory fallbacks.
├── invalidation.py      # Logical Version, Tag-based, and Dependency Graph invalidators.
├── monitoring.py        # Central Hit/Miss metrics and raw Redis info telemetry trackers.
├── services.py          # Background Warmup and Predictive Prefetch services.
├── signals.py           # Django signal listeners for Event-driven invalidation.
└── views.py             # HTTP health-check endpoints for Cache, Redis, and CacheManager.
```

## 3. Cache Access Pattern (Cache Aside & SWR)

We implement the **Cache Aside** pattern with **Stale-While-Revalidate (SWR)**:

1. **Read Request:**
   - The application checks `CacheManager`.
   - **Cache Hit:**
     - The cache is returned instantly.
     - If the **Soft TTL** has expired (but **Hard TTL** has not), a non-blocking background thread is dispatched to rebuild the cache, while the stale value is returned immediately to ensure sub-5ms P95 latency.
   - **Cache Miss:**
     - Only **one** concurrent request acquires a `DistributedLock` to rebuild the cache from PostgreSQL (preventing **Cache Stampede**).
     - Other concurrent requests wait or bypass to PostgreSQL safely.

2. **Write Flow:**
   - The Database is updated successfully.
   - Django database signals fire in `signals.py`.
   - The corresponding Version, Tag, or Dependency is incremented, naturally expiring old cache entries instantly without wildcard deletes.

## 4. Cache Policy Levels

| Level | Name | TTL Range | Typical Targets | Invalidation Strategy |
| :--- | :--- | :--- | :--- | :--- |
| **Level 1** | No Cache | `0s` | Login, JWT, user profile, create/delete, private notifications | Always read from PostgreSQL |
| **Level 2** | Short Cache | `1-15 mins` | Latest articles, popular articles, comments | Invalidated immediately on changes |
| **Level 3** | Medium Cache| `1-12 hours` | Article details, category pages, author profiles, RSS | Soft-rebuild on expiry |
| **Level 4** | Long Cache  | `7-30 days`  | Categories, tags, static pages, menus, settings | Long soft-TTL, signal-driven version increment |

## 5. Pluggable Components

### Serialization
- **MessagePack Serializer:** Binary serialization for maximum speed and minimum storage foot-print.
- **JSON Serializer:** Fallback with custom encoders for ISO-datetime, dates, decimals, and UUIDs.

### Compression
- **Zstandard Compressor:** Highly optimized, fast compression for larger cache payloads.
- **Gzip Compressor:** Native standard backup compressor.
- **Threshold Limit:** Payloads smaller than `2KB` are not compressed to save CPU cycles. Payloads larger than `5MB` are rejected to prevent caching oversized objects.

---

## 6. Distributed Locking with Local Fallback

- Uses atomic Redis `SET NX EX` to acquire distributed locks.
- Safely releases the lock using a Lua script to verify ownership (only deletes if token matches).
- If Redis is down, it falls back transparently to a thread-safe `LocalMemoryLockManager` utilizing python's native re-entrant `threading.Lock`.

---

## 7. Version-Based & Tag Invalidation

To achieve logical invalidation without wildcard deletion:
1. Every cache key generated by `build_cache_key()` is canonicalized and incorporates the current integer version of the associated logical group.
2. If an article belongs to a Category, the cache key incorporates the version of the Category logical Tag.
3. Mutating the category increments the Category tag version. This changes the key generated for all of its articles on future reads, meaning the old entries naturaly expire without ever running a wildcard delete command.

---

## 8. Warmup and Predictive Prefetch

- **Warmup Service:** On content mutation (publish, update, delete), the database signal triggers the Warmup Service to immediately rebuild critical caches (Homepage, category lists, mutated article details, sitemaps). The first visitor never builds the cache.
- **Predictive Prefetch Service:** Periodically (e.g., every 60 seconds), a background thread scans registered hot keys. If any hot key is close to soft-expiry (exceeding 80% of its soft TTL), it pre-emptively refreshes it from PostgreSQL in the background.

---

## 9. HTTP Health Checks and Metrics

Dedicated endpoints are exposed to validate operational status and retrieve telemetry:

- `/health/cache`: Verifies basic Django default cache read/write loops.
- `/health/redis`: Validates live ping connectivity to Redis and returns CPU, Memory usage, fragmentation, evictions, and client count.
- `/health/cache-manager`: Tests serialization, compression, locking, and returns cumulative metrics (Cache Hit Rate, Hit/Miss Ratio, Average Lookup and Rebuild Durations).
